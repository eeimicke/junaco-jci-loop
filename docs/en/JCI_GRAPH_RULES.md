# JCI graph rules

## 1. Status and purpose

This document specifies technology-independent cardinalities and invariants of the JCI graph. The technical meaning comes from [JCI_CONTEXT.md](JCI_CONTEXT.md), the permitted type catalog from [JCI_ONTOLOGY.md](JCI_ONTOLOGY.md). In the event of a conflict, `JCI_CONTEXT.md` applies.

## 2. General entity rules

1. Each concrete `JCIEntity` has exactly one globally unique and immutable UUID as `id`.
2. `entityType` matches the specific entity type.
3. `revision` is a positive integer and starts at `1`.
4. If there is an actual technical change, the previous state is saved as `PiH` and the revision of the current element is increased by exactly one.
5. Every change in professional status is an actual change.
6. `updatedAt` is not before `createdAt`; for immutable entities both values ​​are the same.
7. `PiH`, `ChangeEvent`, `SyncEvent` and `HistoricalCorrection` permanently own `status = RECORDED` and `revision = 1`.
8. These four entity types are not changed, deleted or re-historicized.
9. Empty mandatory fields are not permitted.
10. Professional relationships are saved exclusively as edges and not additionally as ID lists.

## 3. Status rules

| Entity Types | Allowed status values ​​|
| --------------------------------------------------------- | ----------------------------------------------------- |
| `CiV`, `RaN`, `SYNC`, RoF and ERoF graph objects | `DRAFT`, `ACTIVE`, `REPLACED`, `REVOKED` |
| `PiF2`, `PiF1s`, `PiF1t`, `PiF1o` | `DRAFT`, `ACTIVE`, `ACHIEVED`, `REPLACED`, `REVOKED` |
| `Task` | `DRAFT`, `ACTIVE`, `BLOCKED`, `COMPLETED`, `REPLACED`, `REVOKED` |
| `Result` | `DRAFT`, `ACTIVE`, `COMPLETED`, `REPLACED`, `REVOKED` |
| `SuccessCriterion`, `Evidence` | `DRAFT`, `ACTIVE`, `REPLACED`, `REVOKED` |
| `Verification` | `COMPLETED` |
| `RaNConflict` | `OPEN`, `RESOLVED` |
| `PiH`, `ChangeEvent`, `SyncEvent`, `HistoricalCorrection` | `RECORDED` |

There is no transition back to a changeable state from `ACHIEVED`, `REPLACED`, `REVOKED`, `COMPLETED`, `RECORDED` and `RESOLVED`. A continuation is modeled as a new entity.

Binding transition rules:

1. Variable subject entities are created as `DRAFT` and may only become `ACTIVE` after complete validation.
2. `DRAFT` is allowed to change to `ACTIVE` or `REVOKED`.
3. `ACTIVE` is generally allowed to change to `REPLACED` or `REVOKED`.
4. An active future element may become `ACHIEVED` if the target conditions are met.
5. A Task is allowed to change from `DRAFT` or `ACTIVE` to `BLOCKED`. He may switch from `BLOCKED` to `ACTIVE` if the requirements are met or to `COMPLETED` if the closing conditions are simultaneously met.
6. An active Task or an active Result may become `COMPLETED` if the closing conditions are met.
7. A `RaNConflict` is created as `OPEN` and may only change to `RESOLVED` after a confirmed resolution.
8. A `Verification` is immediately created as `COMPLETED` after complete testing.
9. `PiH`, `ChangeEvent`, `SyncEvent` and `HistoricalCorrection` are immediately created as `RECORDED`.
10. Process artifacts and an open `RaNConflict` generated by SYNC do not trigger a recursive `ChangeEvent` for their own generation.
11. Subsequent changes derived deterministically from a change order do not generate their own recursive `ChangeEvent`; they remain traceable via the common `SyncEvent`, `AFFECTS`, Revision and `PiH`.
12. A technical relationship change changes both pre-existing variable endpoints. Both receive a new revision and each a `PiH`; a newly created endpoint in the same order does not yet receive a `PiH`.

## 5. Actor and evidence rules

1. Actors are saved as relationships to `RoleAssignment`; Duplicates of text or ID are not permitted.
2. A functionally active or completed `JCIEntity` has exactly one `CREATED_BY` relationship.
3. `CREATED_BY = 0` is only allowed for bootstrap and import states before technical activation.
4. Each `ChangeEvent` has exactly one `REQUESTED_BY`.
5. Each `HistoricalCorrection` has exactly one `CORRECTED_BY`.
6. Evidence is stored exclusively as `Evidence` nodes and connected via `USES_EVIDENCE`.
7. A `HistoricalCorrection` may exist without `Evidence`, but always requires a non-empty justification.

### 5.1 Traceability rules

1. Each `ACTIVE` or `COMPLETED` atomic Task belongs to at least one complete path via `PiF1t`, `PiF1s` and `PiF2` to at least one `CiV` via exactly one `PiF1o`.
2. Each such Task has exactly one `RESPONSIBLE_TEAM` and at least one valid `EXECUTED_BY` for one `RoleAssignment` of this team.
3. Each executing `RoleAssignment` is uniquely associated with exactly one team, one activated role and exactly one team member; the team belongs exactly to one organization.
4. Environmental relationships of a task must be traceable to at least one acting human or technical identity via its executive role activations.
5. Applicable `RaN` are determined from `GOVERNS`, validity, status and scope; a missing rule path is only permitted if no rule is actually applicable.
6. A `DRAFT` may have incomplete paths. Transitioning to `ACTIVE` is not allowed if the WHY or WHO path is incomplete.

## 6. Organizational and environmental rules

1. Each active `RoFOrg` has at least one team; every active team has at least one member.
2. A `RoleAssignment` belongs to exactly one member, one team and one activated role.
3. The member of a `RoleAssignment` must be a member of the connected team and have the activated role.
4. At least one executing `RoleAssignment` of an active or completed `ATOMIC` task belongs to its `RESPONSIBLE_TEAM`.
5. Each active `ERoFObject` is used by at least one `RoleAssignment`.
6. A direct `Task ── USES ──► ERoFObject` relationship is only allowed for `ATOMIC` tasks and requires that at least one executing `RoleAssignment` uses the same object.
7. `SOURCE_ORG` and `TARGET_ORG` of a `RoFOrgRelationship` must be different.
8. `SUBSIDIARY` is directed and permitted over any number of levels, but must remain cycle-free.
9. `PARTNERSHIP` is technically reciprocal; the stored direction is for clarity only.
10. An active organizational relationship has at least one representative `RoleAssignment` from each participating organization.
11. `HAS_MEMBER` and `HAS_ROLE` have `validFrom` and optionally `validUntil`; the end is not before the beginning.
12. The validity period of a `RoleAssignment` is entirely within a concurrently valid team membership and concurrently valid role ownership.
13. If `allocation` is specified, `0 < allocation <= 1` applies; the sum of simultaneously valid values ​​of a member does not exceed `1`.
14. An active `PARTNERSHIP` stores the organization with the lexicographically smaller UUID as `SOURCE_ORG`.
15. Active organizational relationships of the same type and organizational pair do not have overlapping validity periods.
16. `INTERNAL` or `EXTERNAL` is derived for each organization considered: A `OWNED_BY` edge to it results in `INTERNAL`, its absence `EXTERNAL`.

## 7. RaN priority and conflicts

1. Only `RaN` with `status = ACTIVE`, valid time interval, matching `scopeType`, applicable `APPLIES_IN`, matching `governedTypes` and relevant `GOVERNS` relationship will be considered for a decision.
2. `priority` is a mandatory integer; a larger number means higher priority in an actual contradiction.
3. `ruleType` does not give rise to automatic priority.
4. Agreed applicable rules apply together, regardless of their relative priority.
5. In the case of contradictory rules of different priority, the rule with higher priority applies to the specific contradiction. The other rule remains active outside of this contradiction.
6. If at least two conflicting rules have the same highest relevant priority, exactly one `RaNConflict` with `conflictType = PRIORITY_TIE` arises for the conflict set and decision.
7. If applicability or compatibility cannot be clearly evaluated, a `RaNConflict` is created with `conflictType = UNEVALUABLE`; priority must not ignore uncertainty.
8. An open conflict has a non-empty `conflictKey` that is unique within the change request, at least one `CONFLICTING_RULE`, at least one `AFFECTS`, exactly one `DETECTED_BY`, no `RESOLVED_BY` and no `RESOLVED_THROUGH`. `PRIORITY_TIE` requires at least two conflict rules; For `UNEVALUABLE` at least one rule that cannot be clearly evaluated is sufficient.
9. A resolved conflict has exactly one `RESOLVED_BY`, exactly one `RESOLVED_THROUGH` and one non-empty `resolution` and `resolvedAt`.
10. `RESOLVED` may only be set if a subsequent successful synchronization run confirms that the documented contradiction no longer exists.
11. The change from `OPEN` to `RESOLVED` is a technical change; the open initial state is historicized as `PiH`. `RESOLVED` is terminal.
12. An open conflict blocks automatic changes, the admissibility of which depends on its resolution; independent tests remain possible.
13. `governedTypes` is not empty; each `GOVERNS` target has a listed specific type.
14. `GLOBAL` and `ENTITY` do not have `APPLIES_IN`. `ORGANIZATION` has exactly one relationship to `RoFOrg`; `TEAM` exactly one to `RoFTeam`.
15. Each condition has `combiner = ALL | ANY` and at least one evaluable clause from `path`, `operator` and, if applicable, `value`.
16. `REQUIRE` allowed if the condition is true and denied if the condition is false. `PROHIBIT` denied if condition true. `PERMIT` allowed if condition true. Wrong `PROHIBIT` or `PERMIT` does not make its own decision.
17. A rule violation blocks the requested decision, but by itself does not generate a `RaNConflict`.
18. A contradiction only exists if rules with the same `decisionKey`, overlapping scope and common goal allow and deny at the same time.

## 8. Success criteria and achievement

1. Each `SuccessCriterion` has exactly one `requirementLevel = REQUIRED | OPTIONAL`, one `evaluationMode = ALL | ANY`, one `operator` that matches the `measurementType` and one valid `targetValue`.
2. Unless expressly stated otherwise, `requirementLevel = REQUIRED` and `evaluationMode = ALL` apply.
3. Each `PiF1o` has at least one `REQUIRED` criterion.
4. A current `Verification` is completed and will not be replaced by any other Verification via `SUPERSEDES`.
5. `SUPERSEDES` only connects verifications with the same `Result` and the same `SuccessCriterion`.
6. Verification chains are forward in time, have no branching and are cycle-free.
7. For `evaluationMode = ALL`, a criterion is met if at least one current Verification exists and all current verifications are `VALID`.
8. For `evaluationMode = ANY`, a criterion is met if at least one current Verification is `VALID`.
9. `INVALID`, `INCONCLUSIVE` and a missing current Verification do not meet a criterion; In the case of `ALL`, one of them already prevents fulfillment.
10. Only verifications of results whose tasks belong to the same `PiF1o` as the checked criterion are taken into account.
11. A `PiF1o` may reach `ACHIEVED` if all `REQUIRED` criteria are met, all assigned tasks `COMPLETED`, all Task dependencies are met, all verifications taken into account are completed and all relevant model and `RaN` rules are adhered to.
12. `OPTIONAL` criteria are evaluated and documented, but do not block `ACHIEVED`.
13. `ACHIEVED` is terminal. Later changes to goals, criteria or framework are reflected by a new operational future element.
14. For `BOOLEAN` only `EQUALS` and `NOT_EQUALS` are permitted, for `NUMERIC` only numerical comparison operators are permitted and for `TEXTUAL` only `EQUALS`, `NOT_EQUALS`, `CONTAINS` and `MATCHES` are permitted.
15. A higher future element may only reach `ACHIEVED` if there is at least one current direct contribution and its `contributionMode` is fulfilled: `ALL` requires all, `ANY` at least one direct contribution in `ACHIEVED`.
16. `REPLACED` and `REVOKED` are not considered current contributions. A replacement only counts if it is connected to the same target through `CONTRIBUTES_TO`.

## 9. Task hierarchy, dependencies and status

1. Each Task has exactly one `taskKind = ATOMIC | COMPOSITE`, exactly one `RESPONSIBLE_TEAM` and exactly one operational target context via `PiF1o ── DECOMPOSES_INTO ──► Task`.
2. A `ATOMIC`-Task does not have an outgoing `DECOMPOSES_INTO` relationship with a Task.
3. A `COMPOSITE`-Task has at least one direct subtask and no `EXECUTED_BY`, `USES` or `PRODUCES` relationships.
4. A Task has at most one direct parent Task. Parent Task and subtask belong to the same `PiF1o`.
5. The hierarchy formed by `Task ── DECOMPOSES_INTO ──► Task` is cycle-free.
6. `DEPENDS_ON` may connect tasks of the same or different `PiF1o`, but does not form self-references or cycles.
7. A `DEPENDS_ON` requirement is only met if the target Task is `COMPLETED`. `REPLACED` and `REVOKED` do not meet them.
8. A Task with at least one requirement not met has a `status = BLOCKED`. If all requirements are then met, `SYNC` may redetermine the permissible subsequent status.
9. A `ATOMIC`-Task in `ACTIVE` or `COMPLETED` has at least one `EXECUTED_BY`; at least one of these RoleAssignments belongs to the responsible team.
10. A `ATOMIC`-Task may achieve `COMPLETED` if all prerequisites are completed, execution and team rules are met, relevant `RaN` are met and completion is confirmed. A Result is not a universal closing condition.
11. The status of a `COMPOSITE` task is derived from the effective direct subtasks: only `DRAFT` results in `DRAFT`; all `COMPLETED` result in `COMPLETED`; at least one `ACTIVE` and a mixture of `DRAFT` and `COMPLETED` result in `ACTIVE`; without `ACTIVE`, but with at least one `BLOCKED`, results in `BLOCKED`.
12. A `REPLACED` subtask is only replaced by a successor connected via `REPLACED_BY`, which is itself a direct subtask of the same parent. A `REVOKED` subtask that remains connected or a replacement without this connection creates a conflict.
13. Every derived status change is a technical change and is subject to historization and revision.

## 10. Historization and correction rules

1. Only an actual change to an existing condition creates a `PiH`.
2. `CREATED` does not create a `PiH` for the newly created entity.
3. Each `PiH` maps properties and relationships to exactly one revision of the original entity.
4. A deviation in a `PiH` does not produce a `PiH` of the `PiH`, but rather a `HistoricalCorrection`.
5. The valid historical reading consists of the unchanged `PiH` and its unreplaced corrections.
6. `SUPERSEDES` may only connect corrections of the same `PiH` and must be forward in time and cycle-free.
7. The `CAUSED_BY` event of a correction must be the same event that triggered the `SyncEvent` connected via `CREATES_CORRECTION`.
8. A historical correction does not automatically change the current state of the original entity.
9. A `PiH` contains exactly the properties and incoming and outgoing functional relationships of the specified `originalRevision` that are valid at that time.
10. `contentHash` corresponds to SHA-256 of the canonical serialization of `StateSnapshot` and sorted `RelationshipSnapshot` entries.
11. Each `RelationshipSnapshot` has type, direction, counterpart entity ID, counterpart entity type and a typed property map.
12. `correctedFields`, `previousValue` and `correctedValue` have the same key set; for `ADDITION`, the previous value of the supplemented path is `NULL`.

## 11. SYNC and revision rules

1. A `SyncRun` is technical condition and not a node of the JCI graph.
2. A `SyncEvent` is only created after completion or controlled termination of a `SyncRun`.
3. A failed attempt produces a `SyncEvent` with `outcome = FAILED`.
4. Incomplete technical changes from a failed attempt will be rolled back.
5. `completedAt` of a `SyncEvent` is not before `startedAt`.
6. All counts of a `SyncEvent` are non-negative and match the associated entities.
7. Repetitions may not adopt the same technical change multiple times.
8. `conflictCount` of a `SyncEvent` corresponds to the number of `RaNConflict` objects inversely assigned via `DETECTED_BY`.
9. An entity with `status = REPLACED` has exactly one outgoing `REPLACED_BY` relationship to the same specific entity type.
10. An entity in another state does not have an outbound `REPLACED_BY` relationship.
11. `REPLACED_BY` has no self-references or cycles; a successor may merge several predecessors.
12. For `CONFLICT` or `FAILED`, neither new revisions nor `PiH` arise for states that have not been adopted; the final `SyncEvent` and required `RaNConflict` objects remain separate test documentation.
13. If the storage of a final `SyncEvent` is temporarily technically impossible, it must be made up with the same `runId`, the same `ChangeEvent` and the same idempotence identifier without executing the compartment change again.

## 12. Closed rule status

The status preconditions, cardinalities, traceability, future, Task, RoF, ERoF, RaN, historization and SYNC rules of this version are binding. New domain-specific subtypes may only be added via a versioned model change and must receive their own status preconditions and automated tests before activation.
