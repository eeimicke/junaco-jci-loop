# JCI graph rules

## 1. Status and purpose

This document specifies technology-independent cardinalities and invariants of the JCI graph. The technical meaning comes from [`JCI_CONTEXT.md`](JCI_CONTEXT.md), the permitted type catalog from [`JCI_ONTOLOGY.md`](JCI_ONTOLOGY.md). In the event of a conflict, [`JCI_CONTEXT.md`](JCI_CONTEXT.md) applies.

**Rule package 2.0:** Ontology, graph rules, SYNC, new snapshots, correction values, and the exchange format use version `2.0`. JSON-LD remains `1.1`; existing namespace IRIs ending in `/1.0#` remain stable vocabulary identities and are not the rule version. Earlier records are interpreted only through their explicit version profiles.

## 2. General entity rules

1. Each concrete `JCIEntity` has exactly one globally unique and immutable UUID as `id`.
2. `entityType` matches the specific entity type.
3. `revision` is a positive integer and starts at `1`.
4. If there is an actual technical change, the previous state is saved as `PiH` and the revision of the current element is increased by exactly one.
5. Every change in professional status is an actual change.
6. `updatedAt` is not before `createdAt`; for immutable entities both values ​​are the same.
7. `PiH`, `ChangeEvent`, `SyncEvent` and `HistoricalCorrection` permanently own `status = RECORDED` and `revision = 1`.
8. These four types keep immutable properties and owned provenance and are not deleted or historized again. References owned by another new object follow section 2.2.8 of `JCI_CONTEXT`. Append-only `TRIGGERS` and the successful creation link `CHANGED_BY` do not change an existing `ChangeEvent` revision or timestamps.
9. Empty mandatory fields are not permitted.
10. Professional relationships are saved exclusively as edges and not additionally as ID lists.
11. `ChangeEvent.targetEntityId` and `targetEntityType` are immutable audit coordinates of the accepted request. They do not replace an edge. As soon as a canonical target relationship exists, it must identify the same entity; for a `CREATED` that has not yet succeeded or has failed, the target node may be absent.

## 3. Status rules

| Entity Types                                              | Allowed status values ​​                                         |
| --------------------------------------------------------- | ---------------------------------------------------------------- |
| `CiV`, `RaN`, `SYNC`, RoF and ERoF graph objects          | `DRAFT`, `ACTIVE`, `REPLACED`, `REVOKED`                         |
| `PiF2`, `PiF1s`, `PiF1t`, `PiF1o`                         | `DRAFT`, `ACTIVE`, `ACHIEVED`, `REPLACED`, `REVOKED`             |
| `Task`                                                    | `DRAFT`, `ACTIVE`, `BLOCKED`, `COMPLETED`, `REPLACED`, `REVOKED` |
| `Result`                                                  | `DRAFT`, `ACTIVE`, `COMPLETED`, `REPLACED`, `REVOKED`            |
| `SuccessCriterion`, `Evidence`                            | `DRAFT`, `ACTIVE`, `REPLACED`, `REVOKED`                         |
| `Verification`                                            | `COMPLETED`                                                      |
| `RaNConflict`                                             | `OPEN`, `RESOLVED`                                               |
| `PiH`, `ChangeEvent`, `SyncEvent`, `HistoricalCorrection` | `RECORDED`                                                       |

There is no transition back to a changeable state from `ACHIEVED`, `REPLACED`, `REVOKED`, `COMPLETED`, `RECORDED` and `RESOLVED`. A continuation is modeled as a new entity.

Binding transition rules:

1. Mutable domain entities are created as `DRAFT` and may only become `ACTIVE` after complete validation. Only the six entities of the initial bootstrap under section 12 are created atomically and directly as `ACTIVE`.
2. `DRAFT` is allowed to change to `ACTIVE` or `REVOKED`.
3. `ACTIVE` is generally allowed to change to `REPLACED` or `REVOKED`.
4. An active future element may become `ACHIEVED` if the target conditions are met.
5. A Task is allowed to change from `DRAFT` or `ACTIVE` to `BLOCKED`. He may switch from `BLOCKED` to `ACTIVE` if the requirements are met or to `COMPLETED` if the closing conditions are simultaneously met.
6. An active Task or an active Result may become `COMPLETED` if the closing conditions are met.
7. A `RaNConflict` is created as `OPEN` and may only change to `RESOLVED` after a confirmed resolution.
8. A `Verification` is immediately created as `COMPLETED` after complete testing.
9. `PiH`, `ChangeEvent`, `SyncEvent` and `HistoricalCorrection` are immediately created as `RECORDED`.
10. Process artifacts and an open `RaNConflict` generated by SYNC do not trigger a recursive `ChangeEvent` for their own generation.
11. Subsequent changes derived deterministically from a change order do not generate their own recursive `ChangeEvent`; they remain traceable via the common `SyncEvent`, `AFFECTS`, Revision and `PiH`.
12. Relationship changes follow the endpoint ownership matrix in section 2.2.8 of `JCI_CONTEXT`: only existing mutable owners with an actual delta receive exactly one revision and one `PiH` per request. Verification and audit references do not revise their targets; every graph write remains protected by the technical commit gate.

Conditional invariants:

1. A normal change to an existing historizable entity has exactly one `CHANGED_BY` source.
2. For `CREATED`, the `ChangeEvent` has no `CHANGED_BY` source before the successful commit. Only for `SUCCESS` are the new entity with `revision = 1`, `CREATED_BY`, and exactly one `CHANGED_BY` edge created atomically; for `CONFLICT` or `FAILED`, none of them and no `PiH` are created.
3. A `ChangeEvent` with `changeType = HISTORICAL_CORRECTION` has exactly one `TARGETS_HISTORY`, no `CHANGED_BY` source, and `requestedRevision = 1`. All other change types have no `TARGETS_HISTORY`.
4. An accepted `ChangeEvent` may have `TRIGGERS = 0` while no attempt has finished. Each completed or controlled-aborted `SyncRun` appends exactly one edge; each `SyncEvent` has exactly one triggering `ChangeEvent`.
5. A `SyncEvent` with `SUCCESS` or `CONFLICT` has at least one `AFFECTS` target. Only a `FAILED` attempt that ends before successful target resolution may have no `AFFECTS` target.

**Short example:** A rejected `CREATED` request retains its `ChangeEvent` and receives a `SyncEvent` after the attempt ends, but creates neither the requested target node nor `CHANGED_BY` or `PiH`.

## 5. Actor and evidence rules

1. Actors are saved as relationships to `RoleAssignment`; Duplicates of text or ID are not permitted.
2. A functionally active or completed `JCIEntity` has exactly one `CREATED_BY` relationship, except for the one-time root `RoleAssignment` of the initial bootstrap.
3. Only exactly one root `RoleAssignment` with `bootstrapKey = "ROOT"` may permanently have `CREATED_BY = 0`. For imported entities, its absence is permitted only temporarily while they have `status = DRAFT`.
4. Each `ChangeEvent` has exactly one `REQUESTED_BY`.
5. Each `HistoricalCorrection` has exactly one `CORRECTED_BY`.
6. Evidence is stored exclusively as `Evidence` nodes and connected via `USES_EVIDENCE`.
7. A `HistoricalCorrection` may exist without `Evidence`, but always requires a non-empty justification.

### 5.1 Traceability rules

1. Each `ACTIVE` or `COMPLETED` atomic Task belongs to at least one complete path via `PiF1t`, `PiF1s` and `PiF2` to at least one `CiV` via exactly one `PiF1o`.
2. Each such Task has exactly one `RESPONSIBLE_TEAM` and at least one valid `EXECUTED_BY` for one `RoleAssignment` of this team.
3. Each executing `RoleAssignment` is uniquely associated with exactly one team, one activated role and exactly one team member; the team belongs exactly to one organization.
4. Environmental relationships of a task must be traceable to at least one acting human or technical identity via its executive role activations.
5. Applicable `RaN` are determined from `GOVERNS`, validity, status and scope; a missing rule path is only permitted if no rule is actually applicable.
6. A `DRAFT` may have incomplete paths. Transitioning to `ACTIVE` is not allowed if the WHY or WHO path is incomplete.

## 6. Organizational and environmental rules

1. Each `CiV` describes exactly one value and has non-empty strings for `notCiV`, `selfCiV`, and `toServeCiV`; the former CiV fields `purpose`, `values`, and `scope` are prohibited.
2. Each `CiV` has exactly one `HELD_BY` relationship to a `RoFOrg`, `RoFTeam`, or human `RoFTeamMember`. A technical member is prohibited as value holder.
3. `INFORMED_BY` connects only different CiV after explicit domain confirmation. Equal names, membership, or affiliation create neither an edge nor automatic adoption of dimensions.
4. All CiV directly grounding the same `PiF2` via `INSCRIBES_PURPOSE_IN` have the same `HELD_BY` target. It determines the scope of the `PiF2`; redundant CiV purpose or scope fields are prohibited.
5. An organization-held CiV remains connected to the `RoFOrg`, even when a mandated team develops it. The human decision remains traceable via `CREATED_BY`, `ChangeEvent`, `REQUESTED_BY`, and the participating `RoleAssignments`.
6. Each active `RoFOrg` has at least one team; every active team has at least one member.
7. A `RoleAssignment` belongs to exactly one member, one team and one activated role.
8. The member of a `RoleAssignment` must be a member of the connected team and have the activated role.
9. At least one executing `RoleAssignment` of an active or completed `ATOMIC` task belongs to its `RESPONSIBLE_TEAM`.
10. Each active `ERoFObject` is used by at least one `RoleAssignment`.
11. A direct `Task ── USES ──► ERoFObject` relationship is only allowed for `ATOMIC` tasks and requires that at least one executing `RoleAssignment` uses the same object.
12. `SOURCE_ORG` and `TARGET_ORG` of a `RoFOrgRelationship` must be different.
13. `SUBSIDIARY` is directed and permitted over any number of levels, but must remain cycle-free.
14. `PARTNERSHIP` is technically reciprocal; the stored direction is for clarity only.
15. An active organizational relationship has at least one representative `RoleAssignment` from each participating organization.
16. `HAS_MEMBER` and `HAS_ROLE` have `validFrom` and optionally `validUntil`; the end is not before the beginning.
17. The validity period of a `RoleAssignment` is entirely within a concurrently valid team membership and concurrently valid role ownership.
18. If `allocation` is specified, `0 < allocation <= 1` applies; the sum of simultaneously valid values ​​of a member does not exceed `1`.
19. An active `PARTNERSHIP` stores the organization with the lexicographically smaller UUID as `SOURCE_ORG`.
20. Active organizational relationships of the same type and organizational pair do not have overlapping validity periods.
21. `INTERNAL` or `EXTERNAL` is derived for each organization considered: A `OWNED_BY` edge to it results in `INTERNAL`, its absence `EXTERNAL`.

## 7. RaN protection, priority, and conflicts

1. An active `RaN` has at least one `PROTECTS` to `CiV`, at least one `PROTECTS` to `PiF2`, and at least one `GOVERNS` to a permitted implementation element.
2. Every protected CiV grounds at least one PiF2 protected by the same RaN; every protected PiF2 is grounded by at least one CiV protected by the same RaN. Other CiV of the same PiF2 need not be protected.
3. `PROTECTS` targets only `CiV` or `PiF2`. `GOVERNS` targets only `PiF1s`, `PiF1t`, `PiF1o`, `Task`, `SuccessCriterion`, `Result`, `Verification`, `Evidence`, `RoFOrg`, `RoFOrgRelationship`, `RoFTeam`, `RoFTeamMember`, `RoFRole`, `RoleAssignment`, or `ERoFObject`.
4. `PROTECTS` is created exclusively through an explicit, human-confirmed change traceable to a `RoleAssignment`. `SYNC` does not infer a protection relationship automatically.
5. Protection targets are organizationally compatible with the RaN scope and WHY paths according to `GLOBAL`, `ORGANIZATION`, `TEAM`, or `ENTITY`.
6. Only `RaN` with `status = ACTIVE`, valid time interval, matching `scopeType`, applicable `APPLIES_IN`, matching `governedTypes` and relevant `GOVERNS` relationship will be considered for a decision.
7. `priority` is a mandatory integer; a larger number means higher priority in an actual contradiction.
8. `ruleType` does not give rise to automatic priority.
9. Agreed applicable rules apply together, regardless of their relative priority.
10. In the case of contradictory rules of different priority, the rule with higher priority applies to the specific contradiction. The other rule remains active outside of this contradiction.
11. If at least two conflicting rules have the same highest relevant priority, exactly one `RaNConflict` with `conflictType = PRIORITY_TIE` arises for the conflict set and decision.
12. If applicability or compatibility cannot be clearly evaluated, a `RaNConflict` is created with `conflictType = UNEVALUABLE`; priority must not ignore uncertainty.
13. An open conflict has a non-empty `conflictKey` that is unique within the change request, at least one `CONFLICTING_RULE`, at least one `AFFECTS`, exactly one `DETECTED_BY`, no `RESOLVED_BY` and no `RESOLVED_THROUGH`. `PRIORITY_TIE` requires at least two conflict rules; For `UNEVALUABLE` at least one rule that cannot be clearly evaluated is sufficient.
14. A resolved conflict has exactly one `RESOLVED_BY`, exactly one `RESOLVED_THROUGH` and one non-empty `resolution` and `resolvedAt`.
15. `RESOLVED` may only be set if a subsequent successful synchronization run confirms that the documented contradiction no longer exists.
16. The change from `OPEN` to `RESOLVED` is a technical change; the open initial state is historicized as `PiH`. `RESOLVED` is terminal.
17. An open conflict blocks automatic changes, the admissibility of which depends on its resolution; independent tests remain possible.
18. `governedTypes` is not empty; each `GOVERNS` target has a listed specific type.
19. `GLOBAL` and `ENTITY` do not have `APPLIES_IN`. `ORGANIZATION` has exactly one relationship to `RoFOrg`; `TEAM` exactly one to `RoFTeam`.
20. Each condition has `combiner = ALL | ANY` and at least one evaluable clause from `path`, `operator` and, if applicable, `value`.
21. `REQUIRE` allowed if the condition is true and denied if the condition is false. `PROHIBIT` denied if condition true. `PERMIT` allowed if condition true. Wrong `PROHIBIT` or `PERMIT` does not make its own decision.
22. A rule violation blocks the requested decision, but by itself does not generate a `RaNConflict`.
23. A contradiction only exists if rules with the same `decisionKey`, overlapping scope and common goal allow and deny at the same time.

## 8. Success criteria and achievement

1. Each `SuccessCriterion` has exactly one `requirementLevel = REQUIRED | OPTIONAL`, one `evaluationMode = ALL | ANY`, one `operator` that matches the `measurementType` and one valid `targetValue`.
2. Unless expressly stated otherwise, `requirementLevel = REQUIRED` and `evaluationMode = ALL` apply.
3. Every domain-complete `PiF1o` has at least one current `SuccessCriterion` with `requirementLevel = REQUIRED`. Retired required criteria do not satisfy this minimum.
4. Every `Verification` has positive integers `evaluatedResultRevision` and `checkedCriterionRevision`.
5. A `Verification` evaluates exactly one `COMPLETED` Result and checks exactly one `ACTIVE` SuccessCriterion. At creation and for current goal evaluation, the producing Task and criterion belong to the current scope of the same `PiF1o`.
6. At creation, `evaluatedResultRevision` and `checkedCriterionRevision` exactly match the target revisions checked under the commit gate in section 12.8. Any mismatch causes `CONFLICT`. Under section 2.2.8, `EVALUATES`, `CHECKS`, and the verification’s own provenance do not change those target revisions.
7. An applicable current `Verification` is `COMPLETED`, not superseded through `SUPERSEDES`, and still binds the current revisions of its `COMPLETED` Result and `ACTIVE` criterion. For goal evaluation, the producing Task and criterion must additionally belong to the current scope of the same `PiF1o`.
8. `SUPERSEDES` only connects Verifications with the same `Result` and the same `SuccessCriterion`.
9. Verification chains are forward in time, have no branching, and are cycle-free.
10. For `evaluationMode = ALL`, a criterion is met if at least one applicable current Verification exists and all applicable current Verifications are `VALID`.
11. For `evaluationMode = ANY`, a criterion is met if at least one applicable current Verification is `VALID`.
12. `INVALID`, `INCONCLUSIVE`, and a missing applicable current Verification do not meet a criterion; for `ALL`, one of them already prevents fulfillment.
13. Only Results produced by current Tasks of the same `PiF1o` as the current criterion count. Retired Tasks and criteria retain their stored assignments without counting towards current achievement.
14. A `PiF1o` may reach `ACHIEVED` only if its current Task set is non-empty and entirely `COMPLETED`, at least one current `REQUIRED` criterion exists, every current required criterion is `ACTIVE` and satisfied by applicable current Verifications, and all relevant dependency, WHY, WHO, model, and `RaN` conditions hold.
15. `OPTIONAL` criteria are evaluated and documented but do not block `ACHIEVED`.
16. `ACHIEVED` is terminal. Later changes to targets, criteria, or framework conditions are represented by a new operational future element.
17. For `BOOLEAN`, only `EQUALS` and `NOT_EQUALS` are permitted; for `NUMERIC`, only numeric comparison operators are permitted; and for `TEXTUAL`, only `EQUALS`, `NOT_EQUALS`, `CONTAINS`, and `MATCHES` are permitted.
18. A higher future element may reach `ACHIEVED` only if at least one current direct contribution exists and its `contributionMode` is satisfied: `ALL` requires all direct contributions in `ACHIEVED`, while `ANY` requires at least one.
19. `REPLACED` and `REVOKED` are not current contributions. A replacement counts only if it is itself connected to the same target via `CONTRIBUTES_TO`.

**Short example:** A Verification binds revision 4 of a Result and revision 2 of a criterion. If the criterion changes to revision 3 before commit, the attempt ends with `CONFLICT`. If it changes only later, the Verification remains stored but no longer counts toward the current aggregation.

## 9. Task hierarchy, dependencies and status

1. Each Task has exactly one `taskKind = ATOMIC | COMPOSITE`, exactly one `RESPONSIBLE_TEAM`, and exactly one stored operational goal context through `PiF1o ── DECOMPOSES_INTO ──► Task`; the assignment remains for retired Tasks.
2. An `ATOMIC` Task has no outgoing `DECOMPOSES_INTO` relationship to a Task.
3. A `COMPOSITE` Task has at least one direct subtask and no `EXECUTED_BY`, `USES`, or `PRODUCES` relationships. A current composite has at least one current direct subtask.
4. A Task has at most one direct parent Task. Parent and subtask belong to the same `PiF1o`; a current subtask needs a current parent or an explicit valid reassignment.
5. The stored Task hierarchy remains acyclic.
6. `DEPENDS_ON` may connect Tasks of different `PiF1o`, but forms no self-links or cycles. In addition, the joint completion view of current hierarchy relationships and explicit prerequisites across all reachable goals is acyclic; a mixed cycle causes `CONFLICT` with a cycle witness.
7. A `DEPENDS_ON` prerequisite is satisfied only if its target is `COMPLETED`. `REPLACED` and `REVOKED` remain unmet prerequisites; there is no automatic rewiring to a successor.
8. A released Task in `ACTIVE` or `BLOCKED` with an own unmet prerequisite becomes `BLOCKED`. `DRAFT` requires regular explicit release; terminal Tasks are not reopened.
9. An `ATOMIC` Task in `ACTIVE` or `COMPLETED` has at least one valid `EXECUTED_BY`; at least one of these RoleAssignments belongs to the responsible team.
10. Atomic completion requires satisfied prerequisites, valid execution and team rules, applicable `RaN`, and explicit completion confirmation. A Result is not a universal completion condition.
11. For released composites, an own unmet prerequisite takes precedence and yields `BLOCKED`. Then current direct subtasks determine status: all `COMPLETED` yield `COMPLETED`; at least one `ACTIVE` yields `ACTIVE`; no `ACTIVE` but at least one `BLOCKED` yields `BLOCKED`; only `DRAFT` or `DRAFT`/`COMPLETED` yield `ACTIVE`.
12. Current means neither `REPLACED` nor `REVOKED`; `COMPLETED` remains current. Replacement and revocation require explicit authorization, valid current goal/parent assignment, and non-empty current sets. A retired composite does not hide current descendants.
13. Every actual derived status change is historized and revisioned once per request. Atomic and composite Tasks are evaluated together in prerequisite-before-dependent order.
14. A composite prerequisite is not automatically inherited by subtasks. Additional execution blocking is modelled through explicit prerequisites of the affected Tasks.
15. All operations of a request form one joint candidate graph. Cycle checking and commit validation are protected under section 12.8 of the canonical context document.

## 10. Historization and correction rules

1. Only an actual change to an existing condition creates a `PiH`.
2. `CREATED` does not create a `PiH` for the newly created entity.
3. Each `PiH` captures properties and relationships assigned by the ownership matrix for exactly one revision; new snapshots use profile `2.0`.
4. A deviation in a `PiH` does not produce a `PiH` of the `PiH`, but rather a `HistoricalCorrection`.
5. The valid `HistoryView` applies only active `correctedValue` as absolute overlays on the immutable origin. Superseded operations are not replayed; their earlier `previousValue` is not checked against the origin during reconstruction. This preserves an addition that was subsequently corrected.
6. `correctedFields` follows the closed pointer grammar in section 2.2.9 of the canonical context document. Pointers are unique, canonical, and sorted by Unicode code points; both value maps have exactly the same keys.
7. Non-superseded corrections of one `PiH` have canonical paths that do not overlap with each other or internally under section 2.2.9. Equality and ancestor/descendant relationships count as overlap.
8. No overlap permits no `SUPERSEDES`. Exactly one overlapping active correction must be fully superseded. More than one overlapping active correction causes `CONFLICT` because `SUPERSEDES = 0..1`. A superseding correction belongs to the same `PiH` and contains every canonical field path of its active predecessor unchanged, with its effective value restated. Additional paths do not overlap internally or with any other active correction. `SUPERSEDES` remains temporally forward and acyclic.
9. `SUPERSEDES` connects only corrections of the same `PiH`, is forward in time, and is cycle-free.
10. Snapshot and effective view hash the same canonical `{stateData, relationshipData}` object under profile 2.0. `baseHistoryViewHash` binds the view before acceptance and matches the requested `expectedHistoryViewHash`.
11. `SYNC` serializes all JCI write paths under section 12.8 and recomputes the current `HistoryView` under the gate. A mismatching `expectedHistoryViewHash`, profile error, or path overlap outside the supersession rule causes `CONFLICT` without a correction.
12. The `CAUSED_BY` event of a correction must be the same event that triggered the `SyncEvent` connected via `CREATES_CORRECTION`. This `ChangeEvent` has exactly one `TARGETS_HISTORY` edge to the same `PiH` and no `CHANGED_BY` source.
13. A historical correction does not automatically change the current state of the original entity.
14. A `PiH` contains exactly the owned domain state of `originalRevision` according to its snapshot profile and revision ownership. External revision-neutral documentary references do not rewrite this state retroactively.
15. `contentHash` uses the canonical content object and exact Unicode/number contract in section 2.2.9. Earlier profiles and hashes remain unchanged; unknown or incompatible profiles are rejected.
16. Each `RelationshipSnapshot` has type, direction, other entity ID, other entity type, and typed properties. The stable key projection is unique; corrections do not change relationship identity under an existing key. A whole relationship and its property overlap.

**Short example:** `/stateData/properties/name` and `/stateData/properties/description` are independent. A whole relationship and its `/properties/validFrom` overlap. Such an overlap requires complete supersession of exactly one active predecessor against the current view; overlap with multiple predecessors is rejected.

## 11. SYNC and revision rules

1. A `SyncRun` is technical state and not a node of the JCI graph.
2. An accepted `ChangeEvent` immutably has `idempotencyKey`, `targetEntityId`, `targetEntityType`, and `requestedRevision` and schedules at least one technical `SyncRun`.
3. While no attempt has finished, `TRIGGERS = 0` is permitted. Each completed or controlled-aborted `SyncRun` creates exactly one `SyncEvent` with a unique `runId` and appends exactly one `TRIGGERS` edge.
4. For `CREATED`, the target ID must be free and `requestedRevision = null`. Only `SUCCESS` creates the new target with `revision = 1`, `CREATED_BY`, and exactly one `CHANGED_BY`. No `PiH` is created for that new target; existing mutable owners changed by its domain relationships receive their own `PiH` under section 2.2.8. `CONFLICT` or `FAILED` commits neither the target nor any domain delta or history.
5. For all normal changes, the target must exist and `requestedRevision` must equal its current revision.
6. For `HISTORICAL_CORRECTION`, the target must be an existing `PiH`, `requestedRevision = 1`, `TARGETS_HISTORY = 1`, and `CHANGED_BY = 0`.
7. A failed attempt creates a `SyncEvent` with `outcome = FAILED`.
8. Incomplete domain changes from a failed attempt are rolled back.
9. `completedAt` of a `SyncEvent` is not before `startedAt`.
10. All counts of a `SyncEvent` are non-negative and match the connected entities. `SUCCESS` and `CONFLICT` require `affectedCount >= 1`; only an early `FAILED` before target resolution permits `affectedCount = 0`.
11. Retries must not apply the same domain change more than once; each attempt actually run has its own `runId` and its own `SyncEvent`.
12. `conflictCount` of a `SyncEvent` equals the number of `RaNConflict` objects assigned inversely via `DETECTED_BY`.
13. An entity with `status = REPLACED` has exactly one outgoing `REPLACED_BY` relationship to the same concrete entity type.
14. An entity in any other status has no outgoing `REPLACED_BY` relationship.
15. `REPLACED_BY` has no self-references or cycles; one successor may merge multiple predecessors.
16. For `CONFLICT` or `FAILED`, no new revisions or `PiH` are created for states that were not applied; the final `SyncEvent` and required `RaNConflict` objects remain separate attempt documentation.
17. If storing a final `SyncEvent` is temporarily technically impossible, it must be recorded later with the same `runId`, the same `ChangeEvent`, and the same `idempotencyKey`, without executing the domain change again.
18. The technology-independent exchange format uses `schemaVersion = "2.0"`. `HISTORICAL_CORRECTION` uses a structured payload with `expectedHistoryViewHash` instead of generic `operations`.
19. All JCI write paths use one common technical commit gate per database/model store and increment `graphEpoch` on commit, including revision-neutral evidence. The gate is not a JCI node.
20. The lock is acquired before reading the full relevant graph view. New rules, evidence, edges, absences, and time validity are checked; checking only write-set revisions is insufficient.
21. The complete normalized payload and its immutable identity binding are stored durably. The same identifier with another payload is prohibited; a changed starting revision requires a new request.
22. Run ownership, fencing, and an idempotent commit record prevent duplicate application. With `SUCCESS`, the domain delta, `PiH`, relationships, and `SyncEvent` are persisted atomically with the commit record. Unknown commit outcomes are resolved before retry.
23. All time-dependent checks apply at the documented database decision timestamp immediately before application under the lock. A no-op may return `SUCCESS` with `changedCount = 0`, no new revision, and no `PiH`.

## 12. Initial bootstrap

1. The bootstrap is permitted only once and only in a completely empty graph.
2. It runs in one atomic transaction under the unique pre-initialized technical gate; any error leaves no partial domain graph. Technical gate existence does not violate the empty `JCIEntity` precondition.
3. The minimal graph contains one `RoFOrg`, one `RoFTeam`, one technical `RoFTeamMember`, one `RoFRole`, exactly one root `RoleAssignment` with `bootstrapKey = "ROOT"`, and one `SYNC` definition together with the required RoF relationships.
4. All six bootstrap entities are created directly with `status = ACTIVE`, `revision = 1`, and the same `createdAt` and `updatedAt`. Any `validFrom` values on the types and relationships equal the same bootstrap timestamp. This is the only exception to the regular `DRAFT` start.
5. Only the root `RoleAssignment` may permanently exist without `CREATED_BY`. All other bootstrap entities have exactly one `CREATED_BY` edge to the root `RoleAssignment`.
6. The bootstrap creates neither `ChangeEvent`, `SyncRun`, `SyncEvent`, nor `PiH`.
7. After a successful commit, repetition and a second root `RoleAssignment` are prohibited. All further changes use the normal SYNC process.
8. An import is not a bootstrap. Imported entities without complete provenance remain `DRAFT` until they have been validated through the regular process.

**Short example:** In the empty database, deployment jointly creates the organization, administration team, technical member, role, root assignment, and active SYNC definition. Only after that does the root `RoleAssignment` regularly request the first domain entity.

## 13. Closed rule status

The status preconditions, cardinalities, traceability, future, Task, RoF, ERoF, RaN, historization and SYNC rules of this version are binding. New domain-specific subtypes may only be added via a versioned model change and must receive their own status preconditions and automated tests before activation.
